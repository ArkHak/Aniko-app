# Aniko / AnixKMP — правила работы (AGENTS.md)

Обязательный флоу для **любой** задачи, выполняемой агентом в этом репозитории.
Нарушение флоу ветвления — баг процесса, не деталь.

## Git-флоу выполнения задачи

1. **Подтянуть актуальную базу из remote**:
   `git fetch origin` (не `pull` — база должна быть свежим `origin/<base>`, а не локальной копией).
   База = активная ветка разработки из remote: в этом репо — `origin/main`.
   Если появится `origin/dev` — задачи идут от неё (уточняется у пользователя).
2. **Отвести новую ветку от свежей базы**:
   `git checkout -b <prefix>/<kebab-slug> origin/main`, где префикс по типу работы:
   `feature/` — новая функциональность, `fix/` — багфикс, `docs/` — документация,
   `refactor/`, `chore/` — служебное. Пример: `feature/player-rewind-overlay`.
3. Работать **только** в этой ветке. Никогда не коммитить напрямую в `main`/`dev`.
4. **Чистое дерево перед стартом**: если есть незакоммиченные/незапушенные локальные
   изменения, не относящиеся к задаче — зафиксировать их отдельно (stash/commit на своей
   ветке) и не тащить в новую ветку. Чужую незавершённую работу (пользователя/других
   веток) не трогать.
5. **Коммиты** — английский conventional commit: `feat:`, `fix:`, `docs:`, `chore:`
   (история репо использует именно эти префиксы; номер PR `(#NN)` добавляется при мердже).
6. Валидация перед завершением (см. «Проверка» ниже). После готовности — отчёт: ветка,
   коммиты, что проверено. **Push и создание PR — только по явному решению пользователя**
   (в истории репо принято: ветка готова, «ждёт решения пользователя про коммит/PR»).

## Карта репозитория

- Kotlin Multiplatform + Compose Multiplatform: Android / iOS / Desktop.
- Модули: `shared:model|network|data|player|ui|database`, `composeApp` (точки входа и
  экраны), `iosApp` (Xcode-обёртка), `detekt-rules` (кастомные правила).
- Трекер разработки: **`docs/REELWAVE_PLAN.md`** — статусы фаз, чекбоксы, журнал изменений.
  Работа над функциональностью привязана к фазам/пунктам плана: читать статус перед
  стартом, обновлять чекбоксы/журнал после (через `kmp-dev-doc-writer`).
- API Anixart (реверс-инжиниринг): `docs/api/ANIXART_API.md` + живые сэмплы
  `docs/api/samples/` (используются контрактными тестами).

## Конвенции кода (обязательные)

- MVI: `BaseViewModel<State, Intent, Effect>`; типизированные ошибки → текст выбирает экран
  через i18n, не ViewModel. Koin — DI.
- i18n: все пользовательские строки через `Strings`/`EnStrings`/`RuStrings`
  (`shared/ui/i18n`), детект-правило `ForbiddenCyrillicStringLiteral` запрещает хардкод
  кириллицы вне i18n-слоя.
- `expect/actual` вместо platform checks; commonMain максимален.
- KDoc на public API. detekt + ktlint — чисто (без новых baseline-записей).
- Доступность: `minTouchTarget >= 48dp`, контраст WCAG AA 4.5:1, `contentDescription`
  на интерактивных элементах (паттерн `clearAndSetSemantics`).
- Известный класс багов в проекте: раскладки на `BoxWithConstraints`/`SubcomposeLayout`
  (нулевые constraints, stale-состояние рядом с `AndroidView`) — при новых раскладках
  проверять на живом запуске.

## Проверка (валидация)

- Компиляция затронутых таргетов + линтеры + профильные тесты, например:
  `./gradlew ktlintCheck detektMetadataCommonMain detektDesktopMain :composeApp:compileKotlinDesktop`
  (Android: `compileDebugKotlinAndroid`, iOS: `compileKotlinIosSimulatorArm64`,
  тесты: `:composeApp:desktopTest`, `:shared:data:desktopTest`).
- UI-изменения — живая проверка на реальной поверхности (эмулятор/Desktop-запуск), не только
  компиляция. Ограничение: WebDriverAgent на iOS-симуляторе не видит дерево CMP — iOS
  проверяется визуально (`screen:capture`) или компиляцией.
- Полный `./gradlew clean` + пересборка — при сомнениях в состоянии после параллельной работы.

## Команда KMP Dev

Для делегирования работы используй координатора `kmp-dev` (спавн через `task`, agent:
`kmp-dev`): он сам декомпозирует и распределяет по `kmp-dev-architect` / `kmp-dev-coder` /
`kmp-dev-reviewer` / `kmp-dev-doc-writer`. Данный git-флоу обязателен и для него, и для
всех его воркеров.

## Формат работы с пользователем (2026-09-08)

Пользователь предпочитает **интерактивный режим**: задавай вопросы через `ask` и ЖДИ ответа,
вместо того чтобы молча уходить в длинные автономные прогоны. Крупную работу веди заметными
этапами: экран/фича → офскрин-проверка → коммит → короткий отчёт → следующий этап. Если развилка
меняет объём/вид (например, «делать ли дефолтный вид списком»), лучше один вопрос в диалоге, чем
час работы в неверном направлении.
